# 모바일 제공 형태 결정 기록

> 결정일: 2026-08-26 · 관련 이슈: #4, #11

## 결정

**W.A.V.E는 별도 네이티브 앱을 만들지 않고 반응형 웹 하나로 모바일까지 제공한다.**

앱 프로젝트를 시작할 조건이 충족되기 전까지 이 결정을 유지한다.

## 왜 웹인가

- 현재 운영 주소와 CI·배포·접근성 검사는 Vercel Production의 반응형 웹 하나를
  기준으로 한다. Web App Manifest를 통해 지원 브라우저에서 홈 화면에 설치할 수 있다.
- 이 서비스의 가치는 지도 렌더링 성능이 아니라 **공식 무장애 데이터와 이동
  조건을 교차해 보여 주는 판단 근거**에 있다. 그 부분은 웹에서 이미 동작한다.
- 무장애를 우선하는 서비스에서 두 플랫폼을 병행하면 접근성 검증을 두 벌
  유지해야 한다. 화면 낭독기, 큰 글자, 대비, 초점 이동을 한 벌로 관리하는 편이
  실제 품질에 유리하다.
- 네이티브 프로젝트, 앱 패키지, 스토어 심사 이력이 없다. 웹뷰 포장은 완성도
  이점이 작으면서 권한·딥링크·스토어 정책·기기별 QA 범위를 새로 만든다.

## 앱을 다시 검토할 조건

아래가 **모두** 성립할 때만 별도 앱 프로젝트를 연다.

1. 운영 요구가 앱 패키지 배포를 명시적으로 요구한다.
2. 위치 백그라운드 추적, 푸시, 오프라인 저장처럼 웹으로 대체할 수 없는 기능이
   핵심 평가 요소가 된다.
3. Android/iOS 실기기 QA와 배포 일정을 확보할 인력이 있다.

## 그때 고를 순서

이슈 #4의 조사를 그대로 유지한다. 결론만 옮겨 적는다.

| 순위 | 방식 | 고르는 이유 | 감수해야 하는 것 |
| --- | --- | --- | --- |
| 1 | Kotlin + Jetpack Compose (Android) | Kakao Maps Android SDK v2의 지도·로드뷰·URL Scheme을 공식 방식으로 직접 사용. TalkBack과 Compose semantics로 무장애 품질을 체계적으로 검증 | Android 전용 코드, iOS는 별도 구현 |
| 2 | React Native | 현재 TypeScript 경험·API 타입·검증 로직 일부 재사용, Android/iOS 동시 준비 | 지도·로드뷰가 네이티브 모듈/브리지 품질에 좌우됨 |
| 3 | Kotlin Multiplatform + 플랫폼별 UI | 추천·정렬·API·저장 로직 공유, UI와 지도는 네이티브 | 초기 설계 복잡도와 iOS 개발 환경 필요 |
| 4 | PWA + Trusted Web Activity | 가장 빠른 Play Store 패키지, 웹 업데이트 즉시 반영 | 웹 콘텐츠를 그대로 렌더링하므로 "앱 전용 디자인" 요구와 충돌 |

단순 WebView는 접근성·지도 성능·스토어 품질 면에서 정식 앱의 기본안으로
부적합하다. Flutter는 Kakao 지도 플러그인 유지보수 비용에 비해 기존 TypeScript
자산 재사용 이점이 작아 React Native보다 후순위다.

## 앱을 만들게 되면 지킬 것

웹 레이아웃을 복제하지 않는다.

- 하단 내비게이션 4개: 홈 / 지도 / 내 여행 / 내 정보
- 첫 화면은 섹션형 랜딩이 아니라 지도와 추천
- 장소 카드는 큰 사진과 "휠체어 진입·화장실·엘리베이터" 핵심 3개를 1초 안에
- 혼잡도는 숫자만이 아니라 색·면적·문장으로 중복 표현
- 추천마다 데이터 출처, 기준일, 확인 필요 항목을 펼쳐 볼 수 있게
- 최소 48dp 터치, 큰 글자 200%, TalkBack 탐색 순서, 고대비·색각 이상 테스트
- 자동 사운드·자동 진동 없음. 사용자가 명시적으로 켠 경우에만

## 지금 웹에서 대신 하고 있는 것

앱 없이도 모바일 사용성을 확보하기 위해 이미 반영된 것들이다.

- 360·390·430px 폭, 노치 안전 영역, 44px 터치 영역, 입력 확대 방지, 짧은 가로
  화면 보정 (PR #29)
- 다크 모드, 동작 감소, 파동 효과 끄기
- `app/manifest.ts`의 설치 가능한 웹앱 manifest — 홈 화면 추가로 앱과 비슷한
  실행 경험을 제공한다
