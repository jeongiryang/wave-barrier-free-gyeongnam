# 최신 main 기준 PR 검토 정책

모든 새 PR은 작성자와 변경 종류에 관계없이 병합 직전 최신 `main`을 포함한 HEAD로
다시 검증한다. GitHub가 squash merge 시 최신 `main` 위에 변경을 적용하더라도,
PR 브랜치에서 최신 코드 조합을 검사하지 않았다면 이 기준을 충족하지 못한다.

## 필수 절차

1. `git fetch origin main`
2. `git merge-base --is-ancestor origin/main HEAD` 성공 확인
3. 실패하면 `origin/main` 병합 또는 리베이스
4. typecheck, lint, test, Vercel 빌드 재실행
5. 갱신된 HEAD의 GitHub CI 성공 확인
6. 변경·회귀·보안·접근성·배포 영향 검토
7. 실패나 대기 중인 검사가 없을 때만 병합

## PR 담당자·리뷰어·라벨

- PR 실제 작성자를 assignee로 지정한다.
- PR 작성자를 제외한 기본 협업자 `syt83`, `unknownamed`를 모두 reviewer로 요청한다.
- bot, 권한이 없는 계정, PR 작성자 본인은 reviewer에서 제외한다.
- 저장소의 기존 라벨 체계를 우선하며 모든 PR에 변경 성격에 맞는 라벨을 하나 이상 붙인다.
- 위 metadata는 PR 생성 직후 설정하고 병합 직전에 누락 여부를 다시 확인한다.
- 닫히거나 병합된 과거 PR은 GitHub가 허용하는 assignee·label만 보완하며 형식적인 리뷰 요청은 만들지 않는다.

## 2026-08-18 소급 점검

협업자 PR #14와 #16은 브랜치가 병합 직전 최신 `main`을 포함하지 않은 상태에서
squash merge됐다. 두 변경 모두 충돌 없이 최신 `main` 위에 적용됐지만, 새 조합의
PR CI를 받지 않았으므로 현재 정책에는 미달한다.

병합 후 현재 `main`에서 typecheck, lint, 테스트 8개, Vercel Node 22 빌드와
`git diff --check`를 다시 실행해 모두 성공했으며 실제 회귀는 발견되지 않았다.
이 기록은 절차상 누락과 코드 품질 결과를 구분하기 위해 남긴다.

## 자율 진행 범위

작업 권한이 위임된 변경은 최신 `main` 반영, 전체 로컬 검사와 새 HEAD의 CI 성공을
확인한 뒤 병합한다. 실패·대기 중 검사는 우회하지 않고, 관리자 바이패스는 필수
리뷰 승인 규칙에만 쓴다. 이전 커밋의 성공 결과는 재사용하지 않는다.

독립적인 다음 작업은 `origin/main`에서 시작할 수 있지만, 선행 PR의 결과가 필요한
작업은 그 PR이 병합된 최신 `main`에서 시작해 충돌과 중복을 피한다.

승인된 범위의 완료 조건을 충족할 때까지 진행하되, 모든 오류를 찾았다고 주장하지
않는다. 확인한 코드·화면·검사 범위와 발견하지 못할 수 있는 제약을 함께 기록하고,
범위 밖 문제는 새 이슈로 분리한다.

## 이슈 검토

- 새 이슈는 담당자와 기본 라벨을 지정한 뒤 최신 `main`을 기준으로 중복·적합성·보안·개인정보·모바일·접근성 영향을 검토한다.
- 검토 결과와 구현·보류·종결 판단의 근거를 이슈 코멘트로 남긴다.
- 적합한 이슈만 최신 `main`에서 새 브랜치를 만들고, 기존 PR 검토 절차와 동일한 검증을 거친다.
- 자동 분류 결과가 실제 내용과 다르면 구현 전에 라벨을 바로잡는다.

## 기여자 작업 지침 파일

저장소 규칙 중 자동 검증이 필요한 항목은 이 문서에 둔다. 개별 도구용 작업 지침
파일(`CLAUDE.md` 등)은 각자의 작업 환경에서만 사용하며 저장소에 올리지 않는다.
