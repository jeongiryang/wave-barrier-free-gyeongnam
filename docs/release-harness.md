## 매 작업과 PR

하네스는 짧은 역할 브리프와 검증 계약을 출력하는 로컬 CLI다. LLM·유료 API·에이전트를 호출하거나 이슈·댓글을 자동 생성하지 않는다. 반복 스케줄러나 이슈마다 장문을 재작성하는 자동화도 아니다.

```sh
npm run harness -- status
npm run harness -- brief naru --task 'naru-apply-undo: 대기 중 편의 변경 후 오래된 일정안 적용 차단을 재현하고 고친다'
npm run harness -- brief design --task 'responsive-journey: 390px 나루 입력·제안·도구 복귀의 겹침과 조작 영역을 확인한다'
```

브리프의 사용자 과제와 관련 요구 ID를 먼저 좁힌다. 현재 관련 코드·수용 기준·해당 제출 쪽만 읽고, 매번 전체 문서·전체 이슈·과거 감사 로그를 읽지 않는다. 같은 재현은 한 건으로 묶고 결과에 SHA·환경·영향·재현·기대/실제·증거·다음 행동을 적는다.

구현 중에는 변경 영향에 맞는 검사를 선택한다.

```sh
npm run test:naru
npm run test:api
npm run test:e2e:quick
```

`test:naru`와 `test:api`는 관련 단위·계약 검사 묶음이다. **실제 로컬 모델이나 제공처 성공을 인증하지 않는다.** 작은 변경마다 세 명령을 전부 실행할 필요는 없다. 상태·저장·인증·모델 실행 경계의 변경에는 관련 실패 회귀를 고정하고, 단순 가역적 스타일 수정은 실제 화면을 확인한다.

PR과 main의 빠른 CI는 품질·보안·빌드·성능 예산과 선택된 핵심 브라우저 여정 27개/기기를 검사한다. 브라우저는 desktop/mobile 각 2개 shard, 총 4개 job이다. 과거 PR의 CI 결과를 main에서 재사용하지 않으며 main도 현재 커밋의 빠른 검증을 실행한다. 상세한 배포 게이트와 롤백 기록은 [CI 계약](ci-validation.md)을 따른다.

기존 열린 PR은 하네스·CI/CD 재구축을 먼저 완료한 뒤 새 main과 계약을 반영하여 검증·병합한다. 기존 자동화의 백업 위치·복원 방법·기준 커밋을 CI 기록에 남긴다. 보존된 과거 파일을 활성 워크플로로 되돌리는 일을 일상 검사에서 자동 수행하지 않는다.

## 나루 실제 완주

```sh
npm run check:naru
```

기본은 실행 중인 로컬 앱 `http://127.0.0.1:4173`이며, 승인된 WAVE Production을 확인할 때 `WAVE_NARU_BASE_URL`을 지정한다. 기본 보고서는 `naru-live-result.json`, 변경 경로는 `WAVE_NARU_REPORT`다. 이 검사는 실제 로컬 모델의 의도·일정안·지역과 개수 요청을 확인한다. 실제 호출이므로 명시적인 검증 과제에서 한정해 실행하며 매 PR CI에 자동으로 넣지 않는다.

이 보고서 하나로 나루 완주를 통과시키지 않는다. 같은 후보의 실제 브라우저에서 다음을 독립적으로 확인한다.

1. 개인이 선택한 지역·날짜·필수 편의로 요청하여 실제 관광정보 일정안을 받는다.
2. 장소·날짜·체류·휴식·추천 이유·미확인을 읽고 명시적으로 적용한다.
3. 직접 수정한 뒤 후속 요청을 보내 같은 여행을 유지한다.
4. 장소 보존 부담 조정에서 고정 방문·체류·축제 기간과 전후 비교를 확인한다.
5. 되돌리기, 요청 중 조건 변경, 취소, 모델/API 실패, 빈 결과에서 원래 여행과 복구를 확인한다.
6. 28개 도구 발견·실행·복귀를 확인하고 날짜·장소가 없는 선행 조건을 안내한다.
7. 실제 응답의 첫 반응·완료 지연과 실패 후 회복을 측정하고 사용자가 변경 내용을 이해하는지 검토한다.

모델 출처가 없거나 fallback만 동작하면 `local-llm` 근거는 미통과다. 응답이 빨라도 허위 장소·시설·잘못된 날짜가 적용되면 실패다.

## 9월 30일 최종 감사

빠른 PR 검증은 개발 피드백용이다. 출시 후보에는 [Release Audit](../.github/workflows/release-audit.yml)을 수동 실행하여 전체 품질·보안·빌드·성능과 전체 브라우저 desktop/mobile 각 8개 shard, 총 16개 브라우저 job을 통과시킨다. 제품의 인증·저장·개인정보 경계 단위 검사는 품질 작업에 포함된다. 과거 자동 실행기의 sandbox job은 실행하지 않는다. 로컬 전체 브라우저 검사는 다음 명령을 사용한다.

```sh
npm run test:e2e
```

계획은 9월 26일 재구축·회귀 기준 정리, 27~28일 나루 우선 수정과 제출 기능 검증, 29일 전체 감사·독립 QA·남은 결함 수정, 30일 최종 후보 검증·Production 확인이다. 일정은 목표이며 해당 날짜가 지났다는 이유로 요구를 완료 처리하지 않는다. 최종 수정 후에는 영향받는 검사를 다시 확인하고 최종 후보 SHA에 맞는 전체 감사 근거를 확보한다.

최종 근거는 모든 P0/P1 수용 기준의 실행 결과, 16개 공사 API 및 기타 제공처의 실제 의미 검증, 실제 로컬 모델, 1440px·960px·390px 렌더링, 키보드·화면낭독기·실제 기기, 저장·공유·현장 완주를 포함한다. 공개 영문 화면과 현장 데이터 지역 확대처럼 제출본에 명시한 후속 범위는 현재 완료로 바꾸지 않는다.

```sh
npm run harness -- template release-evidence.json
npm run harness -- release release-evidence.json
```

템플릿은 모든 항목이 미검증인 상태로 생성된다. 각 요구의 필요한 근거 종류를 실제 결과·검토자·확인 시각·증거 파일 또는 URL로 채운다. 전체 감사 run ID, 정확한 후보 커밋, 세 폭의 렌더링, 실제 나루 보고서, 미해결 목록을 함께 제공한다. 상세 JSON 형식의 기준은 생성된 템플릿과 [CLI](../scripts/harness.mjs)다.

`release`는 필수 근거의 존재·현재 커밋·시점과 전체 GitHub 감사 결과를 검증한다. 작성자가 적은 사람·API 검증 주장의 사실 여부를 대신 보증하지 않는다. 근거를 작성한 독립 검토자가 실제 내용을 확인해야 한다. 기존 성공 결과를 복사하거나 `blockers`를 비우는 것으로 미검증 상태를 통과시킬 수 없다.

**FAIL·BLOCKED·UNVERIFIED·필수 근거 누락은 PASS가 아니다.** 외부 쿼터·키 누락·모델 접근 불가도 실제 기능을 확인할 수 없다는 사실과 영향을 남긴다. 최종 자동 감사가 성공해도 실제 제공처·모델·기기 확인이 남으면 출시 완료로 선언하지 않는다. 배포 후 Production의 핵심 여정과 제출 내용의 정합성까지 확인하여 결과를 PR에 남긴다.

## 근거를 짧게 유지하는 규칙

한 번의 브라우저 녹화·렌더링·API 응답이 여러 수용 기준을 직접 검증했다면 같은 증거를 해당 요구 ID에서 참조해도 된다. 항목별로 같은 호출이나 전체 흐름을 반복하지 않는다. 무엇을 확인했는지 알 수 있도록 타임스탬프·단계·결과를 지정한다.

합성·실호출·캐시·수동·자동 검사의 범위를 구분하고 개인 데이터·비밀을 제거한다. 로그는 필요한 재현과 요약, 증거 위치만 남긴다. 새 변경·새 실패·남은 우려가 없으면 같은 검사를 반복하지 않는다. 하네스 운영이 제품 개선 시간을 잠식하면 반복 호출을 줄이고 필수 증거의 정확성을 유지한다.

출시 인증에 사용하는 나루 보고서는 canonical Production의 `/api/health`에서 확인한 현재 커밋과 일치하고 24시간 이내여야 한다. 검사 전후 커밋이 바뀌면 실패한다. 로컬·구버전·필수 사례 누락 보고서는 통과 근거로 받지 않는다.
