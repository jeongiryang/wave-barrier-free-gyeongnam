예상 문구·픽셀을 낮추거나 시간 제한·재시도·skip으로 숨기지 않았다. 이 감사의 7개 실패와 4개 불안정 사례를 모두 분류하여 위 범위에서 보완했다. 후속 로컬 전체 단위검사 1,871개(실패·skip 0), 타입, 소스 lint(임시 `tmp/` 진단 자료 제외, 오류 0·기존 경고 38), 빌드·성능 검사가 통과했다. 최종 로컬 실측은 CSS 126.68/200KiB, 랜딩 JS 151.88/155KiB, 플래너 JS 252.40/270KiB, 최대 chunk 70.44/110KiB다. 소스가 바뀐 새 후보의 전체 감사는 별도로 다시 통과해야 하며 이전 후보의 빠른 CI를 재사용하지 않는다.

### 세 번째 감사와 검사 흐름 보완

`12f9f1a`의 [전체 감사 36476196062](https://github.com/jeongiryang/wave-barrier-free-gyeongnam/actions/runs/36476196062)는 16개 묶음이 모두 완료되어 2,539개 통과·2개 실패·1개 불안정·기존 제외 2개로 끝났다. 제외는 `planner-product-flow`가 desktop 프로젝트에서 여러 화면 폭을 직접 검사하므로 mobile 프로젝트의 중복 실행을 생략하는 기존 계약이며 이번에 추가하지 않았다. 품질·보안·단위·타입·lint·빌드·성능 작업은 성공했다.

- [빠른 CI 36476200828](https://github.com/jeongiryang/wave-barrier-free-gyeongnam/actions/runs/36476200828)의 긴 핵심 여정은 모든 기능과 복원까지 도달했지만 마지막 axe 검사에서 45초 한도가 소진됐다. trace에서 반복 내 여행 진입은 실제 클릭 전에 진행 중인 화면 스크롤의 안정화를 기다렸으며 클릭 유실은 아니었다. 첫 마우스 진입은 유지하고 두 재진입은 실제 키보드 focus/Enter로 검사한다. 이미 선택한 나루 도구는 카탈로그를 다시 거치지 않고 재개 상태를 확인한다. 기존 reduced-motion 설정을 마지막에서 시작으로 옮겨 같은 기능·복원·axe 검사를 일관된 사용자 설정으로 수행한다. 일반 모션은 별도 단계 이동·나루·랜딩 검사에 남는다. 한도·재시도·assertion을 줄이지 않았고 최종 양 기기 2개가 통과했다.
- 양 기기 `naru-keyboard-layout`의 실패는 최신 답변 버튼이 로그 바깥에 있어야 한다는 구형 위치 기대였다. 짧은 화면에서 버튼을 띄운 현재 UI의 180px 초과 대화 영역·44px 버튼·실제 hit-test·마지막 답변까지 읽기·최신 이동 후 숨김·입력창 클릭/입력을 확인하도록 갱신했다. 해당 파일 전체 양 기기 14개가 통과했다. 제품 소스와 CSS는 추가 변경하지 않았다.

- 지역 링크의 불안정한 hit-test는 첫 지역 링크로 이동하던 native 키보드 스크롤에 검사의 instant 중앙 정렬이 겹친 경합이었다. 원본 trace에서 초점 후 페이지가 662px 더 이동했다. CPU 4배 지연 관찰에서도 버튼의 문서상 위치는 일정하고 앱의 추가 scrollIntoView 호출은 없어, 사진 레이아웃 이동이나 앱의 오래된 타깃 복귀와 구분했다. 해당 검사에서 첫 링크가 화면 안으로 들어오고 두 렌더 프레임의 스크롤 위치가 안정된 뒤 기존 44px·hit-test·키보드 확장·18개 지역·출처·axe 검사를 진행한다. 한국어/영어·5개 폭·양 기기 20개가 통과했다.

후속 변경은 검사 세 파일과 기록 문서에 한정하며 앱의 승인 화면·모션은 그대로다. 하네스 구조 검사도 31쪽·79개 요구·기기별 핵심 27개 여정을 유지한다. 이 로컬 결과를 새 후보의 전체 감사 성공으로 표시하지 않으며 정확한 후보 SHA에서 CI와 Release Audit을 다시 실행한다.
