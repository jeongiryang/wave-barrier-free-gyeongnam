# PR-183 — 만료 여행 정리가 사용자 저장 요청을 붙잡던 문제

## 목적

주석은 "한 번에 지우는 양을 제한한다"라고 적혀 있었지만 `DELETE`에 상한이
없었다. 이 정리가 사용자의 저장 요청에 얹혀 있어, 예약 작업이 밀리면 그
청소를 사용자 한 명이 떠안았다.

## 원인

```ts
export async function sweepExpiredTrips(sql: TripSql, now = Date.now()) {
  const rows = await sql`DELETE FROM itineraries WHERE expires_at <= ${now} RETURNING id`;
```

`saveSharedTrip`이 INSERT 직후 이 함수를 기다린다. 예약 작업이 며칠 밀리면
쌓인 만료 행 전체가 한 사용자의 응답 시간이 된다.

## 변경

- `lib/trips/retention.js` — `SAVE_PATH_SWEEP_LIMIT`(20),
  `SCHEDULED_SWEEP_LIMIT`(5000), `sweepLimitFor(trigger)`.
- `server/trips/database.ts` — `id IN (SELECT … ORDER BY expires_at LIMIT n)`.
- `server/trips/itinerary-actions.ts` — 저장 경로는 작은 상한을 명시한다.
- `tests/retention-sweep.test.mjs` — 상한 5건.
- `tests/trip-retention.test.mjs` — SQL 형태 단언 3곳을 새 형태에 맞췄다.

## 설계 판단

**두 호출부에 서로 다른 상한을 줬다.** 예약 작업은 배경이라 넉넉해도 되고,
저장 경로만 묶으면 사용자 지연은 사라지되 정리 처리량은 유지된다.

**`ORDER BY expires_at`을 넣었다.** 상한이 생긴 이상 순서가 없으면 어떤 행은
계속 남을 수 있다.

**주석과 코드의 어긋남 자체를 테스트로 고정했다.** 문서가 지키지 않는 약속을
하면 다음 사람이 잘못 믿는다.

## 결과와 제한

실제 Neon에 만료 행을 쌓아 지연을 측정하지는 못했다. 상한 값은 측정이 아니라
판단이며 `recordOperationalEvent("trip_retention")`의 `deleted` 수치로 조정할 수
있다.

별도 확인 필요: CD가 배포마다 `CRON_SECRET`을 새로 만들어 주입하는데, 이 값이
Vercel cron이 보내는 헤더와 맞지 않으면 정리가 매일 조용히 404가 된다. 핸들러가
인증 실패를 404로 위장하므로 로그도 남지 않는다. 이 PR 범위 밖이지만 그 경우
이번 상한이 더 중요해진다.
