# PR-147 — 공유 여행 보관 기간을 실제로 적용

## 목적

문서가 약속한 30일 만료를 실제 동작으로 만들고, 요청마다 반복되던 스키마
부트스트랩을 한 번만 실행한다.

## 문제

1. **만료된 행이 지워지지 않았다.** `expires_at`은 조회할 때 걸러내기만 했고
   `DELETE FROM itineraries`는 저장소 어디에도 없었다. 인덱스만 있고 정리
   작업이 없어서 행은 영원히 남았다. README의 "30일 뒤 만료"와 실제 동작이
   달랐다.
2. **매 요청마다 DDL을 보냈다.** `ensureTripDatabase()`는 호출될 때마다
   `CREATE TABLE IF NOT EXISTS` 2개와 인덱스들을 Neon으로 왕복했다. 같은
   저장소의 `features/community/server/database.ts`는 프라미스로 캐싱하는데
   trips 쪽만 하지 않았다.
3. **마이그레이션이 커뮤니티만 있었다.** `itineraries`와 `place_feedback`은
   런타임 DDL에만 존재했다. "migration이 진실"이라는 주석과 어긋났다.

## 변경

- `sweepExpiredTrips()` — 만료된 행을 실제로 삭제한다. 저장 요청에 얹어
  실행하고 한 번에 최대 200건으로 끊는다.
- `ensureTripDatabase()`를 `schemaReady` 프라미스로 캐싱. 커뮤니티와 같은 방식.
- `migrations/002_trips.sql` 추가. 런타임 DDL과 같은 내용이며 각 인덱스가
  어떤 질의를 위한 것인지 적었다.
- README의 만료 설명을 실제 동작에 맞게 고쳤다.

## 설계 판단

**별도 스케줄러를 만들지 않았다.** Vercel Cron을 추가하면 배포 구성이 하나 더
늘어난다. 이 저장소는 Vercel Production 하나로만 운영한다는 결정을 유지하고
있으므로, 저장 요청에 얹는 방식이 새 인프라 없이 같은 결과를 낸다.

**한 번에 200건으로 끊었다.** 정리량이 많을 때 한 요청이 오래 붙잡히면 저장
응답이 느려진다. 만료가 밀려 있어도 저장이 일어날 때마다 조금씩 줄어든다.

**정리 실패는 저장을 막지 않는다.** `.catch(() => 0)`으로 삼킨다. 방금 저장한
여행을 돌려주지 못할 이유가 없다.

  처리, 캐싱 방식이 커뮤니티와 같은지, 마이그레이션과 런타임 DDL의 객체 목록이
  일치하는지, README 설명이 실제 동작과 맞는지를 고정한다.

## 영향과 제한

- API 응답 형태 변화 없음.
- 기존 DB에 이미 쌓인 만료 행은 첫 저장 요청부터 200건씩 줄어든다.
- `place_feedback`에는 만료 정책이 없다. 접근성 제보는 운영 자료로 남기는 것이
  현재 정책이며 이 PR에서 바꾸지 않았다.
