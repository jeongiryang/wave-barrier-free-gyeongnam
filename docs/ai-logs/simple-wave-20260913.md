## 목적과 결정

사용자가 기존 여행 설계의 긴 단계, 중복 카드·설명, 추상적인 문구와 나루의 실행 버튼 중심 대화를 지적했다. 협의한 `Simple is Best` 기준으로 여행지 찾기와 내 일정 두 화면을 구현하고, 나루 캐릭터를 유지했다. 소개 첫 화면은 사용자가 선택한 설명 옆 풍경 사진 배치다. 이 배치의 소스 변경은 `a141efb`에 분리했다.

사람은 제품 방향과 실행·배포 범위, 무료 DSW 모델 사용을 결정했다. AI는 코드·문서 수정, 합성 회귀·접근성·성능 검사와 실제 브라우저 조작을 수행했다. 계정·네트워크의 새로운 권한이나 유료 서비스를 추가하지 않았다. 기존 Owner 리뷰 면제를 따르되 실패하거나 대기 중인 필수 CI를 우회하지 않는다.

## 변경

- 전체 폭 공통 메뉴와 두 개의 여행 설계 탭, 상세·편의·수정·출발 정보를 필요할 때 여는 구조로 정리했다.

- 나루와 직접 편집에 같은 일정 명령을 적용한다. 구체적인 수정과 되돌리기, 새 제안 검토·승인, 늦은 응답·반복 적용 방지, 실제 음량을 사용하는 음성 입력과 전송 전 확인을 제공한다.

## 첫 전체 CI 이후 보완

[PR #507의 첫 CI](https://github.com/jeongiryang/wave-barrier-free-gyeongnam/actions/runs/34751897430)는 등록 1,468개 중 1,387 PASS·75 FAIL·5 FLAKY·기존 SKIP 1개였다. quality와 sandbox-boundary는 통과했으나 필수 validate는 실패했으므로 병합하지 않았다. 실패를 개별 재현하고 다음을 수정했다. CI shard·재시도·timeout·성능 예산이나 필수 assertion은 낮추지 않았다.

- 나루 버튼이 일정에 담기 버튼을 가리지 않도록 PC의 옆 여백을 확보했다. 좁은 지도 패널의 이동수단 버튼은 남는 폭에 맞춰 한 열로 배치한다.
- 추천 재검색이 저장한 일정의 지도를 초기화하지 않게 했다. 이동수단 변경 시 일정과 지도에 표시하는 동일 구간은 조회 결과를 공유하며, 다른 지도 구간은 정확한 출발·도착점으로 별도 조회한다.
- 탭을 닫아 둔 사이 완료된 경로는 다시 열 때 즉시 표시한다. 빈 결과·제공처 오류에도 로딩이 끝나고, 기기의 현재 위치는 경로 요청이나 저장 내용에 포함하지 않는다.
- 정보 연결 상태는 내 일정의 여행 도구에서 열 수 있다. 상세 진단 모듈은 실제 펼칠 때만 불러오고 실패해도 일정과 편집을 유지한다.
- 사용 방법 페이지를 두 화면, 날짜 없는 탐색, 수정·나루·저장·공유 메뉴의 실제 조작과 맞췄다.
- 삭제된 다섯 단계·지역 폴리곤·완료 백분율 선택자에 의존한 검사는 지역 격자·선택값·실제 여행 ID/날짜·구간별 근거로 이관했다. SDK의 숨김 상태는 DOM 삭제 대신 접근성 트리·키보드 제외, 동일 지도 노드와 추가 요청 없음으로 검증한다.

보완 과정의 브라우저 검사는 desktop/mobile 각각 workers 1·retries 0으로 수행했다. 소개·출시 흐름 48개, 추천·진단·지역 선택 36개, 일정 구조 44개, 지도 관련 54개, 나루 8개, 나루 버튼 영역 8개를 담당 범위에서 확인했다. 서로 겹치는 단계별 재검사 수치를 하나의 고유 전체 수로 합산하지 않는다. 경로 변경에 영향을 받는 별도 102개 범위도 최종 후보에서 모두 통과했다. 최종 전체 CI의 등록 사례는 1,478개다.

두 개의 로컬 실패는 검증 도중 사용 방법 소스의 HMR이 실제 문서를 교체한 것으로 trace에서 확인했고, 소스 동결 뒤 동일 assertion으로 통과했다. 추가한 검사에서 잘못된 초기 폼 라벨·확인 절차를 기다리는 준비 조건은 실제 사용자 조작으로 고쳤다. JavaScript 비활성 상태는 필수 안내와 숨겨진 마크업의 안전한 URL만 확인했으며, 무스크립트 지역 탐색을 지원한다고 주장하지 않는다.

실제 Chromium 파일 다운로드로 이전 공개 관광 응답에서 담은 장소 `2784088`, `130318`과 `창원의 집` 체류 60분을 확인했다. 이 검사는 공유 API만 의도적인 503으로 격리했으며 Production 공유 검증과 구별한다. 다운로드 파일은 이후 운영 확인의 익명 테스트 여행 복원 자료로 사용한다.

## 세 번째 전체 CI 이후 보완

[세 번째 CI](https://github.com/jeongiryang/wave-barrier-free-gyeongnam/actions/runs/34755656774)는 등록 1,480개 중 1,478 PASS·1 FLAKY·기존 SKIP 1개였다. 단일 지도 검사는 재시도에서 통과했으나 `failOnFlakyTests`에 따라 browser와 validate가 실패했으며 병합하지 않았다. 나머지 7개 browser shard, quality와 sandbox-boundary는 통과했다.

원본 trace에서 390px 변경 직후 `showItineraryMap`의 즉시 visible 조회가 false로 끝나 버튼을 누르지 않은 것을 확인했다. 최종 화면에는 정상적인 보기 전환이 나타났지만 시간표가 선택된 상태였다. 제품의 지도 전환 오류나 HMR이 아닌 검사 준비 경합이었다. 위치 동의와 같은 경합이 있는 지도 도구 검사에서 좁은 화면의 보기 전환 표시를 기다린 뒤 지도 선택·pressed 상태·실제 지도 표시를 확인하도록 이관했다. 공통 helper와 제품 소스는 바꾸지 않았고 timeout·retry·CI 조건은 유지했다. 기존 런타임 언어·GPS 거절 시 좌표 및 route 요청 0회·여행 보존·가로 넘침 검사를 유지하고 44px·1023/1024px·wide→390px 복귀를 확인한다.

수정 후 위치 동의 양기기 4개, 지도 도구 KO/EN 양기기 4개가 통과했다. 위치 동의의 3회 반복 12개는 11 PASS와 화면 캡처 중 브라우저 연결 종료 1개였다. 종료는 시작 약 7.15초·해당 캡처 약 635ms에서 발생하여 45초 test deadline이 아니었고, 정확한 프로세스 종료 원인은 확인되지 않았다. 원본을 보존하고 해당 mobile 사례만 같은 assertion·retry 0으로 다시 확인해 PASS와 정상 browser exit 0을 확인했다. 이를 반복 전체 성공으로 합산하지 않는다. 변경 파일 lint·typecheck·diff check도 통과했으며 최종 전체 CI에서 간헐 실패 없이 완료되는지 다시 확인한다.

기존 SKIP 1개는 `planner-product-flow.spec.ts`가 대표 desktop 프로젝트에서 세 뷰포트를 직접 검증하므로 mobile의 같은 실행을 생략하는 기존 계약이다.

## 배포 전 실제 흐름 검토에서 발견한 공유 안내

[네 번째 CI](https://github.com/jeongiryang/wave-barrier-free-gyeongnam/actions/runs/34756662293)는 배포 검증 스크립트의 독립 검토에서 발견한 공유 안내 결함을 함께 수정하기 위해 시작 약 2분 만에 취소했다. 실패 검사를 우회하거나 성공으로 기록하지 않았다.

실제 여행 파일 다운로드 후 공유 메뉴를 다시 열거나 복사·갱신·종료하면 과거 다운로드 안내가 최신 공유 결과를 가렸다. 수정 전 양 기기에서 안내 7항목이 실패했으며 실제 다운로드 내용, 공개 자료의 개인 정보 제외, 정확한 revision 갱신, 공유 종료와 기존 viewer의 404는 통과해 표시 문제임을 분리했다.

공유 메뉴를 닫거나 열고 링크 복사·갱신·종료를 실행할 때 이전 로컬 안내를 비운다. 다운로드와 별도로 진행되는 공유 링크 오류는 가리지 않으므로 파일 다운로드 성공과 링크 오류를 각각 확인할 수 있다. 권한·revision·저장 데이터를 처리하는 코드는 바꾸지 않았다. 신규 검사는 기본 45초 제한을 유지하며 안내 assertion의 soft 실패도 테스트 실패로 처리한다.

수정 후 신규 양 기기 2개와 기존 공유 회귀 16개가 모두 PASS했다(workers 1·retry 0, 고유 18개). 변경 파일 lint·typecheck·diff check도 통과했다. Production 검증에는 같은 여행/저장 ID에서 나루의 45분 변경이 실제 자동 저장된 뒤 60분으로 되돌아오는지, 실제 assistant 응답의 source/proposal이 무엇인지 확인하는 절차를 추가했다. 모델 출처는 실제 응답을 그대로 기록하며 추정하지 않는다. 최종 등록 브라우저 사례는 1,482개다.

## 배포 영향과 제한

- `013_live_shared_trips.sql`은 기존 공유 일정 테이블에 기본값을 가진 컬럼을 추가한다. 기존 링크는 `live=false`와 기존 만료일을 유지한다. 새로운 환경 변수나 유료 공급자는 없다.
- Production은 기존 GitHub Actions CD만 사용한다. 최종 PR의 전체 검증 성공 후 병합하며 main에서는 동일 tree 증명이 있는 경우에만 브라우저·경계 결과를 재사용한다.
- 전체 개편 롤백은 배포된 PR 변경을 되돌리는 후속 PR과 같은 CD 경로로 진행한다. 추가된 DB 컬럼은 기존 코드와 호환되므로 롤백 때문에 사용자 데이터를 삭제하지 않는다. 첫 화면 배치의 검토 범위는 `landing-split.css`와 `LandingHero`·`LandingHeroCopy`다.
- 실제 관광 제공처가 요청 제한을 반환한 경우를 확인했다. 오류를 정상 빈 결과로 표시하거나 시설 조건을 자동 완화하지 않는다. 이 제한과 로컬 도메인에서 지도 SDK 대신 대체 지도를 사용한 결과는 합성 API 검증과 구별한다.
- 계정 인증·공유 충돌·음성 권한/입력 신호는 통제한 합성 회귀로 확인했다. 실제 사용자의 계정 로그인 및 물리 마이크 녹음을 대신 수행했다고 주장하지 않는다. 전체 다국어·공개 다크 모드, 후속 커뮤니티 AI 기능의 완료 기록으로도 사용하지 않는다.
