# 요청 예산 — 클라이언트가 서버보다 먼저 끊던 문제

## 목적

서버가 정상 응답한 결과를 클라이언트가 먼저 끊어 버리던 문제, 그리고 관광 계획
요청의 서버 소요가 사실상 무제한이던 문제를 함께 고친다.

## 원인

### 1) 예산 역전

클라이언트는 모든 호출에 12초를 썼다(`timeoutMs = 12000`, 어느 호출부도 이 값을
바꾸지 않았다). 그런데 `/api/route`의 상류 타임아웃도 **12초**였다. 상류가 느렸을
뿐 정상 응답한 결과가 클라이언트 예산 밖에서 도착한다.

브라우저에서 재현했다. 서버가 12.5초 뒤 200과 실제 경로를 돌려주는 상황:

```
"느린 경로"가 화면에 있는가: false
타임아웃 문구가 보이는가: true
안내: … 자동차 시간·거리·통행료 준비 중  대중교통 경로 준비 중 …
```

성공한 응답이 버려지고 사용자는 "준비 중"만 봤다.

### 2) 관광 계획의 무제한 소요

`fetchHub`과 `fetchRelated`는 데이터를 찾을 때까지 **월을 거슬러 최대 13번**
반복하고, 매 반복이 시군코드 5개를 병렬 호출한다. `fetchPhoto`도 키워드를 순차로
훑는다. 호출 하나에 건 9.5초 타임아웃으로는 전체가 잡히지 않는다.

| 단계 | 최악 |
| --- | --- |
| 1단계 (지역목록·두루누비·허브·사진) | 123.5초 — `fetchHub`이 13개월 순차 |
| 2단계 (상세 6건 병렬) | 9.5초 |
| 3단계 (오디오·연관·혼잡) | 123.5초 — `fetchRelated`가 13개월 순차 |
| **합계** | **256.5초** |

클라이언트 12초는 물론 Vercel 함수 실행 한도도 넘는다.

## 변경

- `lib/request-budget.js` — 상류 타임아웃, 경로별 서버 예산, 그것을 감싸는
  클라이언트 예산을 한 곳에서 정한다. `withinBudget`, `budgetClock` 포함.
- 서버 8개 파일의 `AbortSignal.timeout(숫자)`를 공용 상수로 바꿨다.
  교통 상류는 12초 → 9.5초로 관광 쪽과 맞췄다.
- `server/tourism/plan-builder.ts` — 요청 전체에 12초 예산을 두고 단계마다 남은
  예산을 다시 잰다. 못 끝낸 항목은 실패한 조회로 남아 기존 상태 표시에 그대로
  드러난다. 지어내지 않는다.
- 클라이언트 호출부가 경로별 예산을 쓴다(`plan`·`enrich`·`route`·`crowd`·`location`).
- `tests/request-budget.test.mjs` — 불변식 9건.
- `e2e/slow-upstream.spec.ts` — 서버 예산을 거의 다 쓴 응답이 화면에 닿는지.
- `tests/repository-policy.test.mjs` — 리터럴을 검사하던 단언 4곳을 상수 기반으로
  갱신했다. 의도(타임아웃이 존재한다)는 그대로다.

## 설계 판단

**클라이언트를 늘리지 않고 서버를 묶었다.** 256초를 감싸려면 클라이언트가
259초여야 하는데, 그만큼 기다리게 하는 것은 답이 아니다. 서버가 자기 예산을
책임지고, 클라이언트 타임아웃은 그 위의 안전망으로 둔다.

**예산 초과를 실패가 아니라 "확인 못 함"으로 다뤘다.** `buildPlan`은 이미 개별
조회 실패를 견디도록 만들어져 있다. 예산을 넘긴 단계는 실패한 조회와 같은 모양을
돌려주므로, 사용자는 부분 결과와 함께 무엇을 확인하지 못했는지 본다. 예전에는
클라이언트가 12초에 끊어 **아무것도** 못 봤다.

**두 값을 한 파일에 두고 관계를 테스트로 고정했다.** 서버와 클라이언트 값이 다른
파일에 흩어져 있으면 한쪽만 바뀌어 다시 역전된다. 여유를 0으로 바꿔 보면
`클라이언트는 서버보다 늦게 끊는다`가 실패하는 것을 확인했다.

## 결과와 제한

실제 상류로 측정하지 못했다. 인증키가 없어 한국관광공사·ODsay·카카오모빌리티
응답 시간을 직접 재지 못했고, 최악값은 코드의 반복 구조와 타임아웃 상수로
계산했다. 12초라는 계획 예산이 실제 응답 분포에 맞는지는 배포 후
`recordOperationalEvent("tourism_plan")` 로그로 확인해야 한다.

교통 상류를 12초에서 9.5초로 낮췄으므로, ODsay·카카오모빌리티가 9.5초를 넘겨
응답하던 경우는 이제 실패로 처리된다. 그 경우 예전에도 클라이언트가 12초에
끊어 사용자에게는 결과가 닿지 않았다.
