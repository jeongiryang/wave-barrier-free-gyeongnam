# PR-170 — 스키마 준비가 한 번 실패하면 그 인스턴스가 영구히 죽던 문제

## 목적

Neon 콜드스타트 지연이나 일시적 네트워크 오류로 런타임 DDL이 한 번 실패하면,
그 서버리스 인스턴스가 회수될 때까지 커뮤니티와 공유 여행의 **모든** 요청이
같은 오류를 돌려주던 문제를 고친다.

## 원인

두 모듈 모두 준비 **Promise 자체**를 캐시했다. 성공했을 때 요청마다 DDL 왕복이
붙지 않게 하려는 최적화인데, 거부된 Promise까지 캐시되고 되돌리는 경로가 없었다.

```ts
if (schemaReady) return schemaReady;
schemaReady = (async () => { ... DDL ... })();
// 거부돼도 schemaReady = null 로 되돌리는 곳이 없음
return schemaReady;
```

같은 구조를 그대로 재현해 확인한 결과:

```
요청 1: 실패 — Neon 콜드스타트 타임아웃
요청 2: 실패 — Neon 콜드스타트 타임아웃
요청 3: 실패 — Neon 콜드스타트 타임아웃
요청 4: 실패 — Neon 콜드스타트 타임아웃
실제 DDL 시도 횟수: 1        ← 다시 시도하지 않는다
```

다른 인스턴스는 멀쩡하므로 사용자에게는 "가끔 커뮤니티가 안 열린다"로만 보이고
재현하기 어렵다. 커뮤니티는 콜드스타트마다 DDL을 14번 왕복하므로 실패 확률도
그만큼 높다.

## 변경

- `lib/schema-bootstrap.js` — `createSchemaBootstrap(prepare)`. 성공한 준비만
  재사용하고, 거부되면 캐시를 비워 다음 요청이 다시 시도하게 한다. 동기적으로
  던지는 준비도 거부로 다룬다.
- `server/trips/database.ts`, `features/community/server/database.ts` —
  이 방식을 쓴다. DDL 내용은 그대로다.
- `tests/schema-bootstrap.test.mjs` — 동작 5건.
- `tests/trip-retention.test.mjs` — 기존 구조 단언을 새 형태에 맞췄다.
  "한 번만 실행한다"는 의도는 그대로이고, 이제 실행 횟수를 동작으로 센다.

## 설계 판단

**성공 캐싱은 유지했다.** 요청마다 DDL을 다시 보내면 실제 작업 전에 왕복이
여러 번 붙는다. 기존 최적화의 의도는 옳았고, 빠진 것은 실패 경로뿐이다.

**공용 모듈로 뺐다.** 두 파일에 같은 수정을 따로 넣으면 다음에 세 번째 저장소가
생길 때 또 빠뜨린다. `lib/*.js`에 두면 CI의 Node 22.13에서도 `node --test`로
동작을 직접 검증할 수 있다.

**동시 요청은 같은 시도를 공유한다.** 세 요청이 겹쳐 들어와도 준비는 한 번만
돌고, 그 시도가 실패하면 셋 다 같은 오류를 받은 뒤 캐시가 비워진다. 실패마다
DDL이 폭주하지 않으면서 다음 요청은 회복된다.

## 검증

- `npm run lint` 통과 (경고 0)
- `npm run typecheck` 통과 (오류 0)
- `npm test` 통과 (113/113, 신규 5건)
- `npm run build:vercel` 통과
- `npm run test:e2e` — 21/22. 실패 1건은 이 변경과 무관한 기존 flake
  (`landing-regions`, PR #163에서 고침). 단독 실행하면 2/2 통과한다. 변경 파일은
  서버 DB 모듈과 테스트뿐이라 랜딩 마커 좌표에 영향을 줄 수 없다.

## 결과와 제한

실제 Neon에 대고 실패를 일으켜 보지는 못했다. 재현과 검증은 같은 캐싱 구조를
그대로 옮긴 코드로 했다. DDL 문 자체와 마이그레이션 파일은 건드리지 않았다.
