# PR-172 — "저장"이 저장했다고만 말하고 아무 일도 하지 않던 문제

## 목적

지도 도구의 `☆ 저장`이 아무도 읽지 않는 저장소 키에 써 놓고
"현재 여행 경로를 이 기기에 저장했습니다"라고 알리던 문제를 고친다.
사용자는 저장됐다고 믿고 다시 와서 아무것도 찾지 못했다.

## 원인

`wave-saved-map` 키는 저장소 전체에서 **쓰는 곳 1군데, 읽는 곳 0군데**였다.

```
features/routing/useMapJourneyActions.ts:48  window.localStorage.setItem("wave-saved-map", ...)
— 읽는 곳 없음
```

복원 화면도, 목록도, 어떤 진입점도 없었다.

## 확인

브라우저에서 재현했다. Kakao 지도가 연결된 상태에서만 열리는 패널이라 실제 SDK
대신 최소 스텁을 넣어 그 상태를 만들었다.

| | 수정 전 | 수정 후 |
| --- | --- | --- |
| 저장 직후 헤더 보관함 | 0 | 2 |
| 새로고침 뒤 헤더 보관함 | 0 | 2 |
| `wave-saved-map` | 값이 쌓임 | 쓰지 않음 |

  담을 것이 없거나 이미 다 담겨 있으면 그렇게 말한다.

  이미 담긴 곳은 건너뛰고 새로 담은 수를 돌려준다. 일정 배정도 함께 만든다.

## 설계 판단

**지우지 않고 동작하게 했다.** 버튼을 없애는 쪽이 diff는 작지만, 사용자가 보던
기능을 말없이 빼는 것은 제품 결정이라 임의로 하지 않았다. 반대로 "지키지 못할
약속을 지키게 만드는 것"은 명백한 개선이다.

**이미 동작하는 보관함에 연결했다.** `wave-saved-places`는 새로고침을 견디고,
헤더에 개수가 보이며, 일정 배정과 공유 링크로 이어진다. 두 번째 저장 개념을
새로 만들 이유가 없다.

**콜백으로 넘겼다.** `features/routing`이 플래너의 저장소 키를 직접 건드리면
경계가 무너진다. 기존 `onChoosePoint`·`onMapDestination`과 같은 방식이다.

**정책 테스트는 의도를 유지하며 갱신했다.** 기존 검사는 옛 구현의 형태
(`places.slice`)를 보고 있었다. 지금은 지도가 저장소에 직접 쓰지 않는지,
보관함이 문자열 ID만 남기는지를 본다. 좌표 변수를 하나 넣어 보면 여전히
실패하는 것을 확인했다.

## 결과와 제한

저장 직후 지도 배지의 안내 문구는 지도가 다시 그려질 때 덮인다. 이는 별도
작업 단위(PR #164, 스크롤이 지도를 다시 만드는 문제)에서 다루므로, 이번
브라우저 테스트는 문구 대신 남는 결과(보관함 개수·저장소 내용)로 확인한다.

`☆ 저장`은 `▱ 레이어·측정` 패널 안에 있고 이 패널은 Kakao 지도 연결 상태에서만
열린다. 대체 지도(OSM)로 떨어진 사용자는 이 버튼에 도달할 수 없다. 이 접근
경로 문제는 이번 범위 밖이다.
