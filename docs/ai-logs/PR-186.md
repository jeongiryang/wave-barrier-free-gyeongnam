# PR-186 — Vercel Cron 인증 값을 프로젝트 환경으로 고정

## 목적

공유 여행 30일 보관 정책의 예약 정리가 Vercel Cron에서 실제로 인증되어 실행되도록
배포 계약을 바로잡는다.

## 발견한 문제

기존 CD는 Production 후보를 만들 때마다 `openssl rand -hex 32`로 새 `CRON_SECRET`을
만들고 `vercel deploy --env CRON_SECRET=...`로 해당 배포 런타임에만 덮어썼다.

Vercel 공식 Cron 계약은 다르다. `CRON_SECRET`을 **Vercel 프로젝트 환경 변수**로
설정하면 Vercel 스케줄러가 그 프로젝트 값으로 `Authorization: Bearer <secret>`을
보내고, 함수도 `process.env.CRON_SECRET`으로 같은 프로젝트 값을 비교한다.

따라서 프로젝트에 값이 없거나, 프로젝트 값과 배포별 override가 다르면 예약 호출이
인증에 실패할 수 있다. CD health는 일반 `/api/health`만 확인하므로 이 문제를 잡지 못한다.

## 변경

- `.github/workflows/cd.yml`
  - `vercel env ls production`으로 프로젝트 Production `CRON_SECRET` 존재 여부 확인
  - 없으면 64자리 hex 난수를 Vercel의 sensitive Production 환경 변수로 한 번 생성
  - 이후 `vercel pull --environment=production`을 다시 실행해 동일 프로젝트 환경 동기화
  - 배포마다 만들던 `cron_token`/`CRON_SECRET --env` 제거
  - 일회성 `COMMUNITY_MIGRATION_TOKEN`만 후보 배포에 주입
- `lib/deployment/production-env.js`
  - `CRON_SECRET`을 Production 필수 환경 계약에 포함
  - 런타임에서도 32자 미만이면 배포 검증 실패
- `.env.example`, `docs/vercel-neon-setup.md`
  - Project Production 환경 변수로 관리한다는 운영 규칙 명시
  - 현재 001~004 migration 절차도 함께 동기화
- `tests/deployment-gates.test.mjs`, `tests/trip-retention.test.mjs`
  - 프로젝트 secret 보장 로직은 있어야 하고 배포별 CRON override는 없어야 한다는 회귀 단언 추가

## 안전성

secret 값은 출력하거나 저장소/GitHub Secret에 복제하지 않는다. 새 값이 필요한 경우
GitHub Actions의 기존 Vercel 인증으로 Vercel Project Settings에 sensitive 변수로 직접
등록하고 셸에서도 즉시 마스킹한다. 기존 프로젝트 값이 있으면 변경하지 않는다.

## 근거

2026-08-29 확인한 Vercel 공식 문서 `Managing Cron Jobs`는 `CRON_SECRET`을 Vercel
프로젝트에 추가하며 그 값이 Cron 호출의 Authorization 헤더로 자동 전송된다고 명시한다.
`vercel deploy --env` 공식 문서는 해당 옵션이 배포 런타임 환경 변수를 제공한다고 설명한다.
즉 둘을 별개의 값으로 운용하면 안 된다.
