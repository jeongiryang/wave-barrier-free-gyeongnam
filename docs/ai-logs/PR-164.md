# PR-164 — 스크롤만 해도 지도가 다시 만들어지던 문제

## 목적

플래너 지도가 데이터 변화 없이 반복해서 파괴·재생성되던 문제를 고친다.
사용자가 맞춰 둔 확대·이동과 지도 위에 그린 측정 도형이 스크롤할 때마다
사라지고, `/api/map-config` 요청과 지도 로딩 상태가 반복해서 깜빡였다.

## 원인

`RouteMapWorkspace`가 매 렌더 새 배열을 만들어 넘기고 있었다.

```tsx
<RouteMap places={activePlaces.slice(0, 6)} ... />
```

`.slice()`는 내용이 같아도 매번 새 참조를 만든다. 이 값은
`useMapRenderer`의 `useEffect` 의존성 배열에 들어 있어, 참조가 바뀌면
cleanup → `/api/map-config` 재요청 → 지도 재초기화 → `setBounds()`가 다시 돈다.

`usePlannerChrome`이 스크롤 방향에 따라 `headerHidden`을 토글하므로,
**스크롤만 해도 페이지가 리렌더되고 지도가 통째로 다시 만들어졌다.**

## 브라우저 측정 (1440×960)

`/api/map-config` 호출 횟수와, 살아 있는 지도 DOM에 남긴 표식의 생존 여부로 쟀다.

| --- | --- | --- |
| 최초 렌더까지 재생성 | 7회 | 3회 |
| 위아래 스크롤 8회 이후 추가 재생성 | **7회** | **0회** |
| 지도 인스턴스 생존 | 사라짐 | 유지 |

## 변경

- `features/planner/components/RouteMapWorkspace.tsx` — 잘라낸 배열을 `useMemo`로
  감싸 `activePlaces`가 실제로 바뀔 때만 새 참조를 준다.
- `e2e/planner-map-stability.spec.ts` — 스크롤이 지도를 다시 만들지 않는지 고정한다.

## 설계 판단

**호출부에서 참조를 고정했다.** `useMapRenderer`의 의존성 배열을 손대는 방법도
있지만, 그러면 의존성이 실제로 쓰는 값과 어긋나 다음 사람이 읽기 어려워진다.
불안정한 입력은 `places` 하나뿐임을 확인했다 — `origin`·`activeRoute`·`crowd`는
상태이거나 이미 `useMemo`로 감싸여 있고, 콜백은 모두 `useCallback` 또는 setState다.

**남은 3회는 이 PR의 범위 밖이다.** 최초 렌더의 3회는 각각 추천 목록·경로·혼잡도가
도착하는 실제 데이터 변화에 대응한다. 이걸 없애려면 렌더러를 "지도 생성"과
"마커·경로 갱신"으로 쪼개야 하며, 별도 작업 단위로 남긴다.

## 결과와 제한

지도 렌더러 내부 구조는 바꾸지 않았다. cleanup이 Leaflet만 정리하고 Kakao
인스턴스·리스너·오버레이는 해제하지 않는 문제는 그대로 남아 있으며, 재생성
빈도가 줄어 영향은 작아졌지만 별도 작업 단위로 다뤄야 한다.
