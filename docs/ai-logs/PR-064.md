# PR #64 · 서버 제공기관과 공통 경계 분리

## 발견

`worker/index.ts`가 API routing뿐 아니라 환경 변수 해석, 공통 응답·입력 검증,
Open-Meteo 날씨 변환과 Kakao 장소 검색까지 직접 구현하고 있었다. 제공기관 하나를
수정할 때 entrypoint 전체를 읽어야 했고, 공통 보안 경계를 독립적으로 찾고 검증하기
어려운 구조였다.

## 구현

- `server/shared/env.ts`: 서버 환경 변수 타입과 런타임 해석을 분리했다.
- `server/shared/http.ts`: JSON 응답, 문자열 정제, 안전한 HTTPS URL 변환과
  Origin·Fetch Metadata·본문 크기 검증을 공통 경계로 분리했다.
- `server/weather/handler.ts`: 지역 좌표, 날씨 코드 해석, 일정 조언과 Open-Meteo
  요청을 날씨 제공기관 모듈로 옮겼다.
- `server/location/handler.ts`: Kakao 장소 검색, timeout, 응답 정규화를 독립 모듈로
  옮겼다.
- `worker/index.ts`는 분리한 handler를 route에 연결하는 orchestration 역할을
  유지하며 1,479줄/약 84KB에서 1,311줄/약 74KB로 줄었다.
- 공통 요청 보안과 제공기관 timeout이 새 모듈에 유지되는지 repository 회귀 테스트를
  추가했다.
- README의 저장소 구조를 실제 server 경계와 일치시켰다.

## 역할 구분

- 사람: 동작을 유지하며 제공기관별 책임과 공통 서버 경계를 점진적으로 분리하라는 기준 위임
- 도구: worker 책임 감사, 모듈 분리, 회귀·빌드·배포 검증

## 배포 영향과 제한

- API route, 응답 schema, 환경 변수와 DB schema는 변경하지 않는다.
- 날씨와 장소 검색은 기존 timeout·오류·cache 정책을 그대로 유지한다.
- TourAPI와 교통 제공기관은 다음 점진적 분리 단위로 남긴다. 한 PR에서 worker 전체를
  재작성하지 않아 배포 위험과 검증 범위를 제한했다.
