# PR-169 — 한국어가 아닌 화면에서 테마 선택이 무시되던 문제

## 목적

English·日本語·中文·Français·Deutsch·Русский로 보는 사용자가 자연·역사·레저·미식
테마를 바꿔도 다국어 관광정보 쪽 결과가 그대로이던 문제를 고친다.

## 원인

`buildPlan`은 지역 목록을 두 서비스에서 가져와 합친다. 무장애 서비스
(`KorWithService2`)는 테마 조건이 들어간 `locationParams`를 쓰는데, 언어 서비스는
한국어일 때만 같은 값을 쓰고 그 외에는 별도 객체를 만들어 넘겼다.

```ts
locale === "ko"
  ? locationParams                                              // contentTypeId 있음
  : { ...commonParams("12"), arrange: "Q", lDongRegnCd: "48" }  // contentTypeId 없음
```

두 분기는 `contentTypeId` **하나만** 다르다. 그 값이 자연(12)·역사(14)·
레저(28)·미식(39)을 가르는 유일한 키다.

결과가 무장애 서비스 쪽과 합쳐지기 때문에 목록이 완전히 같지는 않고, 그래서
"테마가 아예 안 먹는다"보다 "가끔 엉뚱한 장소가 섞인다"로 보였다. 사용자가 고른
테마와 무관한 장소가 테마에 맞는 것처럼 제시되는 상태다.

## 근거

이 줄은 최초 커밋(`c051667`)부터 있었고 그 뒤 두 번의 리팩터링에서 위치만
옮겨졌다. 의도를 밝힌 주석도, 다국어 데이터가 희소해 일부러 조건을 푼다는
기록도 없다.

## 변경

- `server/tourism/plan-builder.ts` — 로케일 분기를 없애고 두 서비스가 같은
  `locationParams`를 쓴다. 남은 차이는 서비스 이름뿐이다.
- `tests/plan-locale-theme.test.mjs` — 두 `areaBasedList2` 호출이 같은 조회
  조건을 쓰는지, 그 조건에 `contentTypeId`가 들어 있는지 고정한다.

## 설계 판단

**분기를 고치지 않고 없앴다.** 다국어 분기에 `contentTypeId`만 더하면 두 객체가
글자 하나 빼고 같아진다. 같은 값을 두 번 적어 두면 한쪽만 바뀌는 일이 반복된다.

**결과 수가 줄 수 있다는 점은 감수한다.** 다국어 관광정보는 국문보다 등록 건수가
적어, 테마 필터를 걸면 후보가 줄 수 있다. 다만 이 서비스의 결과는 무장애 서비스
결과와 합쳐지고 무장애 쪽은 이미 테마로 걸러져 있으므로 기본 후보는 유지된다.
수를 채우려고 테마와 무관한 장소를 섞는 쪽이 이 저장소의 원칙("임의의 장소를
대신 표시하지 않는다")에 어긋난다.

## 결과와 제한

실제 한국관광공사 응답으로 로케일별 결과 수를 비교하지는 못했다. 인증키가
없어 상류를 호출할 수 없다. 배포 후 다국어 화면에서 테마를 바꿔 결과가
실제로 달라지는지, 그리고 후보 수가 지나치게 줄지 않는지 확인이 필요하다.
