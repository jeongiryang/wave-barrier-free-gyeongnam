# PR-149 — 아무도 불러 쓰지 않는 배럴 모듈 제거

## 목적

임포트되지 않는데 테스트가 붙잡고 있어서 남아 있던 모듈 두 개를 지우고,
같은 상황이 다시 생기지 않게 하는 검사를 넣는다.

## 문제

`server/tourism/models.ts`는 세 모듈을 재수출하는 배럴이었다.

```ts
export { placeFrom } from "./accessibility-model";
export { audioFrom, courseFrom, richSpot } from "./content-model";
export { apiStatus, mergePlaces } from "./provider-model";
```

저장소 전체에서 이 파일을 임포트하는 곳은 없다. 유일한 참조는
`tests/repository-policy.test.mjs`가 이 파일을 **읽어서 문자열을 검사**하는
부분이었다. 소스 문자열 단언 방식의 테스트가 죽은 코드를 살려 두고 있었다.

가드 테스트를 넣자 같은 모양이 하나 더 나왔다.
`features/community/server/repository.ts`도 임포트되지 않는 배럴이었고,
`tests/auth-community.test.mjs`만 이 파일을 읽고 있었다.

## 변경

- `server/tourism/models.ts` 삭제. 테스트는 배럴의 재수출 문장 대신 각 도메인
  모듈이 실제 함수를 내보내는지 확인하도록 바꿨다.
- `features/community/server/repository.ts` 삭제. 관련 단언 제거.
- `tests/module-reachability.test.mjs` 추가.

## 가드 테스트

`components`, `features`, `lib`, `server`의 모든 모듈이 어딘가에서 임포트되는지
확인한다. `app/`은 프레임워크가 파일 경로로 라우팅하고 `scripts/`는 CLI로
실행되므로 대상에서 뺐다.

임포트 문의 경로를 실제로 해석해서 비교한다. 파일 이름만 비교하면 같은 이름의
모듈(`types.ts`, `database.ts`, `api.ts`)끼리 서로를 가려 준다. 상대 경로를
저장소 기준 경로로 풀고 확장자를 정규화한 뒤 대조한다.

## 설계 판단

`server/tourism/photos.ts`도 재수출 모듈이지만 **실제로 임포트되므로** 남겼다.
이번 작업의 기준은 "배럴인가"가 아니라 "아무도 불러 쓰지 않는가"다.
